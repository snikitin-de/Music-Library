# AGENTS.md

## Назначение репозитория

Репозиторий предназначен для безопасной обработки музыкальной библиотеки:

- проставление тегов через `beets`;
- раскладка файлов по исполнителям и альбомам;
- поиск дублей;
- выбор файла с лучшим качеством;
- перенос худших дублей в карантин, а не удаление.

## Главные правила для агента

1. Никогда не удаляй музыкальные файлы без отдельного явного подтверждения пользователя.
2. По умолчанию используй только безопасный режим:
   - `dry-run`;
   - копирование вместо перемещения;
   - перенос дублей в папку карантина.
3. Перед массовой обработкой всегда показывай план действий.
4. Перед изменением тегов или переносом файлов сначала запускай проверку на небольшой выборке.
5. Все операции должны быть обратимыми.
6. Все действия фиксируй в отчётах:
   - CSV;
   - лог в консоли;
   - при необходимости JSON.
7. Не меняй исходную папку без явного разрешения.
8. Не трогай файлы, если невозможно уверенно определить исполнителя, альбом или трек.

Исключение: веб-действие `layout` в режиме `Реальная обработка` может перемещать файл внутри текущей библиотеки только после явного подтверждения пользователя, с обновлением HTML/CSV-отчётов и без удаления исходных данных за пределами этой библиотеки.

## Кодировка и git

Чтобы не тратить время на повторяющиеся проблемы с кодировкой и git:

- Считай все текстовые файлы проекта UTF-8.
- В PowerShell для чтения и записи файлов с русским текстом явно указывай UTF-8:
  - чтение: `Get-Content -LiteralPath <file> -Raw -Encoding UTF8`;
  - запись: `Set-Content -LiteralPath <file> -Encoding UTF8`.
- Если вывод PowerShell выглядит как `РќР°...`, сначала проверь файл через `git show HEAD:<path>` или другой UTF-8-совместимый способ чтения, а не переписывай файл вслепую.
- Не исправляй “битую кодировку”, пока не проверено, что испорчены именно байты файла, а не только вывод консоли.
- Перед изменениями проверяй `git status --short` и не трогай чужие изменения в рабочем дереве.
- Для просмотра различий используй `git diff -- <file>`; для уже закоммиченной версии - `git show HEAD:<file>`.
- Не используй `git reset --hard`, `git checkout -- <file>` и похожие команды для отката без явного разрешения пользователя.
- Не коммить и не пушь изменения без отдельной просьбы пользователя.
- Если нужно отредактировать файл с кириллицей, предпочитай точечный патч и после правки проверяй, что `git diff` показывает читаемый русский текст.

## README и документация

Чтобы репозиторий не засорялся временными README-файлами:

- Основной README должен быть только один: `README.md` в корне проекта.
- Не создавай дополнительные файлы вида `README_*.md`, `README-*.md` или README в подпапках без отдельной просьбы пользователя.
- Если нужно зафиксировать результат работы, дополняй корневой `README.md`, `CHANGELOG.md` или файл в `reports/`, в зависимости от смысла.
- Временные пояснения по исправлениям не сохраняй отдельными README-файлами; кратко описывай их в ответе пользователю или в отчёте.
- Если найден некорневой или временный README, сначала проверь, что он не является единственным источником важной инструкции, затем предложи перенести полезное содержимое в корневой `README.md` или профильный отчёт.

## Правила тегирования

Для тегирования использовать `beets`.

Основной сценарий:

1. Импортировать музыку из исходной папки.
2. Подтянуть теги через MusicBrainz.
3. Записать теги в файлы.
4. Скопировать обработанные файлы в отдельную папку.
5. Не удалять исходники.

Запрещено по умолчанию:

```text
move: yes
delete: yes
```

Разрешено по умолчанию:

```text
copy: yes
write: yes
timid: yes
```

## Правила раскладки файлов через beets

Эти правила относятся к обычному импорту через `beet -c beets-config.yaml import ...`.

Стандартная структура:

```text
$albumartist/$year - $album/$track - $title
```

Для одиночных треков:

```text
Singles/$artist/$title
```

Для сборников:

```text
Compilations/$year - $album/$track - $title
```

Важно: в основном `beets-config.yaml` раскладка безопасная — `copy: yes`, `move: no`. Исходники остаются на месте, обработанная библиотека копируется в каталог `directory` из конфига.

## Веб-операции из HTML-отчёта

HTML-отчёт может запускать обработку музыки через `scripts/report_server.py`. Для этих операций действуют дополнительные правила:

- Глобальные кнопки работают только с текущим отфильтрованным списком:
  - `Проставить теги для отфильтрованных`;
  - `Разложить отфильтрованные по папкам`.
- Кнопки внутри карточки работают только с файлом своей карточки `.music-card`:
  - `Проставить теги`;
  - `Разложить по папкам`.
- API `/api/music-operation` должен получать параметр `scope`:
  - `scope: single` — ровно один файл;
  - `scope: filtered` — список файлов из текущего фильтра.
- Если `scope: single` получает больше одного файла, сервер должен вернуть ошибку и не запускать обработку.
- Реальная обработка всегда должна требовать подтверждение в интерфейсе. `dry-run` остаётся режимом по умолчанию.

Для действия `layout` в веб-отчёте не полагайся на `beet import`: он может пропустить файл как уже импортированный или дубль. Актуальная логика раскладки должна:

1. читать теги файла через `mutagen`;
2. брать текущую папку библиотеки из HTML-отчёта;
3. проверять, что файл находится внутри этой библиотеки;
4. строить путь назначения по тегам;
5. не перезаписывать существующие файлы, а добавлять номер вида `(2)`;
6. в `dry-run` только показывать план;
7. в реальном режиме перемещать файл только после явного подтверждения пользователя.

Текущий формат веб-раскладки:

```text
Исполнитель альбома/Альбом/Название - Исполнитель альбома.ext
```

Этот формат отличается от стандартного `paths` в `beets-config.yaml`. В веб-раскладке не добавляй год и номер трека, пока текущая реализация `scripts/report_server.py` использует именно такой путь.

Fallback-значения:

```text
Unknown Artist
Unknown Album
```

Для корректной раскладки нужны теги:

- `albumartist` или `artist`;
- `album`;
- `title`;
- желательно `date/year` и `tracknumber`.

После реальной раскладки обязательно обновляй пути:

- в списке музыки внутри `reports/library.html`;
- в `reports/duplicates.csv`, если перемещённый файл участвовал в дублях;
- в карточке HTML-отчёта, если операция была запущена для одной записи;
- в кэше сервера.

Важно: обновление путей после раскладки не пересчитывает группы дублей. Для полного пересчёта дублей нужно снова запустить `scripts/find_duplicates.py`, затем пересобрать HTML-отчёт.

Веб-сервер отчёта также поддерживает безопасные действия с файлами:

- `Переместить всё в карантин` переносит только `moved_file` из текущего `reports/duplicates.csv`.
- Кнопка `В карантин` у конкретного файла переносит выбранный файл из текущей группы дублей.
- Кнопка переноса в `Trash` не удаляет файл, а перемещает его в папку `Trash` рядом с библиотекой.
- Любой перенос через сервер должен требовать явный confirmation-token в API и записывать действие в `reports/file_actions.csv`.
- После карантина или Trash HTML-отчёт и CSV дублей обновляются без полного пересканирования.
- `Пересканировать библиотеку` запускает новый поиск дублей и пересборку HTML-отчёта; это отдельное действие с явным подтверждением.

## Правила поиска дублей

Дубли определяются по нормализованным тегам.

Для альбомных треков:

```text
albumartist + album + track + title
```

Для одиночных треков:

```text
artist + title
```

Текущий `scripts/find_duplicates.py` дополнительно использует:

- fallback по имени файла, если теги прочитать нельзя или их недостаточно;
- проверку точных копий по хэшу содержимого;
- отдельный CSV `*_needs_review.csv` для похожих случаев, которые нельзя уверенно считать дублями.

Перед сравнением нужно нормализовать строки:

- привести к нижнему регистру;
- убрать лишние пробелы;
- убрать повторяющиеся разделители;
- заменить `ё` на `е`;
- убрать технические пометки, если они мешают сравнению.

## Выбор лучшего файла

Лучший файл выбирается по рейтингу качества.

Приоритет:

1. Lossless-формат:
   - FLAC;
   - ALAC;
   - WAV;
   - AIFF.
2. Битрейт.
3. Bit depth.
4. Sample rate.
5. Полнота тегов.
6. Наличие встроенной обложки.
7. Больший размер файла, если остальные признаки равны.

Пример приоритета:

```text
FLAC > ALAC > WAV > AIFF > AAC > MP3 > OGG > WMA
```

Текущий скрипт также учитывает `M4A` и `OPUS`: `M4A/AAC` выше `MP3`, `OPUS` выше `OGG`, но lossless-форматы всё равно выше любых lossy-форматов.

MP3 320 kbps обычно лучше MP3 192 kbps, но FLAC лучше любого MP3.

## Правила обработки дублей

По умолчанию:

- лучший файл остаётся на месте;
- худшие дубли переносятся в папку `Duplicates`;
- создаётся CSV-отчёт;
- ничего не удаляется.

CSV-отчёт должен содержать колонки:

```text
duplicate_group
kept_file
moved_file
reason
kept_quality
moved_quality
```

## Особые случаи

Не считать дублями автоматически:

- album version и single version;
- remaster и original;
- radio edit и full version;
- live и studio;
- explicit и clean;
- разные релизы одного альбома;
- разные исполнители при одинаковом названии песни.

Такие случаи лучше выносить в отчёт как `needs_review`.

По умолчанию файл такого отчёта создаётся рядом с основным CSV как `duplicates_needs_review.csv`, если не указан `--review-report`.

## Команды

Установка зависимостей:

```bash
pip install -r requirements.txt
```

Проверка дублей без переноса:

```bash
python scripts/find_duplicates.py --library "D:\Music\Sorted" --dry-run
```

Перенос худших дублей в карантин:

```bash
python scripts/find_duplicates.py --library "D:\Music\Sorted" --quarantine "D:\Music\Duplicates"
```

Перенос только одного найденного дубля:

```bash
python scripts/find_duplicates.py --library "D:\Music\Sorted" --quarantine "D:\Music\Duplicates" --only-file "D:\Music\Sorted\Artist\Album\Track.flac"
```

Импорт через beets:

```bash
beet -c beets-config.yaml import "D:\Music\Unsorted"
```

Запуск локального сервера HTML-отчёта:

```bash
python scripts/report_server.py --open
```

Перерисовка HTML из встроенного payload без повторного сканирования сетевой библиотеки:

```bash
python scripts/rerender_html_report.py --html "reports\library.html"
```

## Ожидаемое поведение агента

Если пользователь просит “удалить дубли”, агент должен сначала предложить безопасный вариант:

```text
Сначала перенесу худшие дубли в Duplicates и сделаю CSV-отчёт.
Удалять файлы сразу не буду.
```

Если пользователь просит “разложить музыку”, агент должен использовать копирование, а не перенос:

```text
Исходники останутся на месте.
Обработанная библиотека будет скопирована в Sorted.
```

## HTML-отчёт

Если пользователь просит красивый отчёт, используй:

```bash
python scripts/generate_html_report.py --csv "reports\duplicates.csv" --out "reports\library.html"
```

Требования к HTML-отчёту:

- файл должен быть автономным;
- не требовать внешних CSS/JS;
- работать локально в браузере;
- показывать сводку;
- поддерживать поиск;
- поддерживать сортировку;
- показывать список всей музыки, если отчёт собран с `--library`;
- поддерживать фильтр по тегам и статусу раскладки;
- поддерживать пересканирование библиотеки через локальный сервер;
- поддерживать безопасный перенос дублей в карантин через локальный сервер;
- показывать сравнение `оставлен` / `в карантин`;
- не содержать действий удаления файлов.


## Требования к внешнему виду HTML-отчёта

- Не закрепляй панель поиска при прокрутке.
- Все пользовательские подписи в отчёте должны быть на русском.
- Технические музыкальные параметры показывай так: формат, битрейт, разрядность, частота дискретизации, теги, обложка, размер.

## Анализ всей музыкальной папки в HTML-отчёте

Если пользователь просит общий анализ папки с музыкой, генерируй отчёт с параметром `--library`:

```bash
python scripts/generate_html_report.py --csv "reports\duplicates.csv" --library "D:\Music\Sorted" --out "reports\library.html"
```

На странице отчёта должны быть метрики:

- всего файлов;
- альбомов;
- исполнителей;
- дублей.

Дубли считать по CSV-отчёту поиска дублей. Файлы, альбомы и исполнителей считать сканированием папки `--library`.
